# Пакеты и модули в Go

**Главное:**
- **Пакет (package)** — базовая единица компиляции. Группа связанных функций, типов, структур. Каждая папка — **отдельный пакет**.
- **Модуль (module)** — набор связанных пакетов, управляемый системой модулей. **Один проект — один модуль** (кроме монорепо).
- Связь: **модуль содержит пакеты**, пакеты содержат код.

## Пакет vs Модуль

| | Пакет | Модуль |
|---|---|---|
| Что это | Единица **компиляции** | Единица **зависимостей** |
| Где | Папка с `.go` файлами | Репозиторий с `go.mod` |
| Идентификатор | `package mathutils` в каждом файле | `module github.com/user/project` |
| Масштаб | Малый (одна ответственность) | Большой (проект целиком) |
| Пример | `mathutils`, `auth`, `database` | `github.com/user/myproject` |

## Именование пакетов

| Правило | Пример |
|---|---|
| Маленькие буквы | `mathutils`, не `MathUtils` |
| Краткие, но информативные | `auth`, не `authenticationhelper` |
| `_` допустимо | `math_utils` — работает, но редко |
| **Одна ответственность** | Не `utils`, а `mathutils`, `dbutils` |

⚠️ **`utils` — плохое имя.** Слишком абстрактно. Дроби по назначению: `stringutils`, `fileutils`, `mathutils`.

## Экспорт: заглавная vs строчная

| Идентификатор | Доступ |
|---|---|
| `Add`, `User`, `Config` (Заглавная) | **Из других пакетов** ✅ |
| `subtract`, `user`, `config` (строчная) | **Только внутри пакета** ❌ |

```go
// mathutils/math.go
package mathutils

func Add(a, b int) int { return a + b }        // экспортируется
func subtract(a, b int) int { return a - b }   // приватный
```

```go
import "github.com/user/myproject/pkg/mathutils"

result := mathutils.Add(3, 4)        // ✅
result := mathutils.subtract(3, 4)   // ❌ ошибка компиляции
```

**То же правило**, что в теме структур/методов — **регистр = видимость**.

## go.mod — манифест модуля

```go
module github.com/user/myproject

go 1.23

require (
    github.com/sirupsen/logrus v1.9.0
    golang.org/x/crypto v0.5.0
)
```

| Строка | Что значит |
|---|---|
| `module` | Путь к модулю (для импортов) |
| `go` | Версия Go, под которую собирается проект |
| `require` | Зависимости и их версии |

**Создание:**
```bash
go mod init github.com/user/myproject
```

## go.sum — контрольные суммы

```
github.com/sirupsen/logrus v1.9.0 h1:trlNQbNUG3OdDrDil03MCb1H2o9nJ1x4/5LYw7byDE0=
github.com/sirupsen/logrus v1.9.0/go.mod h1:naHLuLoDiP4jHNo9R0sCBMtWGeIprob74mVsIT4qYEQ=
```

**Зачем:** защита от подмены зависимости (злоумышленник не подсунет другой код под ту же версию).

**Правило:** `go.mod` и `go.sum` — **коммитятся в git**. Всегда.

## Команды для работы с модулями

| Команда | Что делает |
|---|---|
| `go mod init <path>` | Создаёт новый модуль (создаёт `go.mod`) |
| `go get <pkg>` | Добавляет / обновляет зависимость |
| `go get <pkg>@v1.2.3` | Установить конкретную версию |
| `go get -u <pkg>` | Обновить до последней версии |
| `go get -u` | Обновить **все** зависимости |
| `go mod tidy` | Удаляет неиспользуемые, добавляет недостающие |
| `go mod vendor` | Создаёт `vendor/` с копиями зависимостей |
| `go list -m all` | Показать все зависимости |
| `go mod graph` | Граф зависимостей |

**`go mod tidy` — самая частая команда.** Запускай после добавления/удаления кода, который использует зависимости.

## Стандартная структура проекта

```
myproject/
├── go.mod
├── go.sum
├── cmd/
│   └── app/
│       └── main.go
├── internal/
│   ├── auth/
│   │   ├── auth.go
│   │   └── auth_test.go
│   └── database/
│       ├── db.go
│       └── db_test.go
├── pkg/
│   ├── mathutils/
│   │   ├── math.go
│   │   └── math_test.go
│   └── logutils/
│       └── logger.go
├── api/
│   ├── proto/
│   │   └── service.proto
│   └── openapi.yaml
└── README.md
```

| Папка | Назначение |
|---|---|
| **`cmd/`** | Точки входа (`main.go`). Каждое приложение — своя папка |
| **`internal/`** | **Приватный** код — **нельзя** импортировать извне модуля |
| **`pkg/`** | Публичные библиотеки — можно импортировать из других проектов |
| **`api/`** | Описания API: `.proto`, `openapi.yaml`, GraphQL-схемы |
| **Тесты** | Рядом с кодом, суффикс `_test.go` |

### `internal/` — ключевая фишка

```
myproject/
├── internal/
│   └── auth/         ← доступен ТОЛЬКО внутри myproject
└── pkg/
    └── mathutils/    ← доступен снаружи
```

**Правило:** всё, что **не должно быть видно снаружи** — в `internal/`. Go **не даст** импортировать `internal/` из другого модуля — **ошибка компиляции**.

## init() — функция инициализации

**Что это:** служебная функция, вызывается **автоматически до `main()`**. Подготавливает окружение: глобальные переменные, соединения, регистрация обработчиков.

### Особенности init()

| Особенность | Деталь |
|---|---|
| Не требует вызова | Go вызывает сам |
| Без аргументов и возврата | `func init() { ... }` |
| Может быть **несколько** | В одном файле, в разных файлах пакета |
| Где угодно | Даже в `main`-пакете |

```go
func init() {
    // настройка логгера
    // регистрация драйвера БД
    // чтение конфига
}
```

### Порядок инициализации программы

Go идёт **снизу вверх** по цепочке импортов.

Если `main` → `pkg1` → `pkg2` → `pkg3`:

1. Сначала `pkg3` (самый глубокий).
2. Затем `pkg2`.
3. Затем `pkg1`.
4. Затем `main`.
5. Только потом — `main()`.

### Внутри **каждого** пакета — строгий порядок

```
1. const
2. var (с инициализацией)
3. init()
```

### Пример

```go
package main

import "fmt"

var x = initX()   // 2. var

func initX() int {
    fmt.Println("var инициализируется")
    return 10
}

func init() {     // 3. init
    fmt.Println("init выполняется")
}

func main() {     // 4. main
    fmt.Println("main")
}

// Вывод:
// var инициализируется
// init выполняется
// main
```

⚠️ **Не выноси в `init()` сложную логику.** Трудно тестировать, неявно, порядок зависит от импортов. Лучше — явная инициализация в `main()` или конструктор.

## Рекомендации

| № | Правило |
|---|---|
| 1 | Одна папка — один пакет. Одна ответственность |
| 2 | Имена пакетов — маленькие буквы, кратко, конкретно (`mathutils`, не `utils`) |
| 3 | `go mod tidy` — после каждого изменения зависимостей |
| 4 | `go.mod` и `go.sum` — **в git** |
| 5 | `cmd/` — для точек входа, `internal/` — для приватного, `pkg/` — для публичного |
| 6 | API-описания — в `api/` |
| 7 | Тесты — рядом с кодом, `_test.go` |
| 8 | `init()` — минимальный, без сложной логики |

## Подводные камни

### 1. Циклические импорты **запрещены**

```go
// package a
import "b"   // a → b

// package b
import "a"   // b → a   ❌ цикл, ошибка компиляции
```

**Как разрывать:**
- Вынести общий код в **третий пакет** (`common`, `types`).
- Использовать **интерфейсы** — объявить в одном пакете, реализовать в другом.

### 2. `internal/` — жёсткое правило

Попытка импортировать `internal/` из **другого модуля** → **ошибка компиляции**. Не «warning», не «в рантайме» — сразу.

### 3. `go.sum` удалять нельзя

Если удалишь `go.sum` — `go build` пересоздаст его, но **проверка подписи** может упасть, если нет доступа к прокси. **Не трогай.**

### 4. Не коммить `vendor/` без причины

`vendor/` — **дублирует** зависимости в репо. Нужен, если:
- Сборка **без интернета**.
- Фиксация **точных версий** без `go.sum`.

**По умолчанию** — не коммитится.

### 5. `init()` не тестируется

Нельзя **вызвать `init()` явно** в тесте. Если логика в `init()` — её **не протестировать**. Отсюда правило: `init()` — минимальный.

### 6. Импорт модуля = **путь**, не имя папки

```go
import "github.com/user/myproject/pkg/mathutils"
//                       ↑ путь из go.mod, а не просто "mathutils"
```

Внутри модуля — можно и относительные пути, но **принято** использовать **полный путь** из `go.mod`.

## Запомнить

- **Пакет** — папка с `.go` файлами. **Модуль** — проект с `go.mod`.
- **Один проект — один модуль.**
- **Заглавная буква** = экспорт, **строчная** = приватность внутри пакета.
- **Циклические импорты запрещены.** Разрывай через общий пакет или интерфейсы.
- **`go.mod`** — манифест модуля. **`go.sum`** — контрольные суммы. **Оба — в git.**
- **`go mod tidy`** — убирает лишнее, добавляет нужное.
- **`cmd/`** — точки входа. **`internal/`** — приватное. **`pkg/`** — публичное. **`api/`** — описания API.
- **`internal/`** — нельзя импортировать из другого модуля (ошибка компиляции).
- **`init()`** — автоматический вызов до `main()`.
- **Порядок инициализации:** зависимости → `const` → `var` → `init()` → `main()`.
- **`init()` — минимальный.** Сложную логику — в явные конструкторы.

# Управление инструментами (tools)

**Главное:** сторонние инструменты (генераторы, линтеры, форматтеры) нужно **фиксировать по версиям**, иначе у разных разработчиков — разные результаты. С **Go 1.24+** для этого есть директива **`tool` в `go.mod`**. Раньше использовали **`tools.go`** с build-тегом.

## Зачем фиксировать версии инструментов

| Проблема | Что случается |
|---|---|
| Несогласованность | Разные версии генератора → разный код |
| Несовместимость | Обновление ломает поведение |
| Сложная диагностика | У одного работает, у другого нет |

**Фиксация даёт:**
- Стабильность разработки.
- Идентичность окружения у команды.
- Простой CI/CD.

## Старый подход: `tools.go` (до Go 1.24)

Файл в корне проекта:

```go
//go:build tools
// +build tools

package tools

import (
	_ "golang.org/x/tools/cmd/stringer"
)
```

**Как работает:**
- `//go:build tools` — файл **не компилируется** при обычной сборке.
- Импорт через `_` — «зависимость без использования».
- Go видит, что модуль **зависит** от инструмента — версия фиксируется в `go.mod`.

**Установка:**

```bash
go get golang.org/x/tools/cmd/stringer@latest
go mod tidy
go install golang.org/x/tools/cmd/stringer
```

Бинарник появится в `$GOBIN` (обычно `~/go/bin`).

## Новый подход: директива `tool` (Go 1.24+)

```bash
go get -tool golang.org/x/tools/cmd/stringer@v0.33.0
```

В `go.mod` появится:

```
module github.com/user/myproject

go 1.24.3

tool golang.org/x/tools/cmd/stringer

require (
	golang.org/x/mod v0.24.0 // indirect
	golang.org/x/sync v0.14.0 // indirect
	golang.org/x/tools v0.33.0 // indirect
)
```

**Установка всех tools:**

```bash
go install tool
```

— устанавливает **все** инструменты из `go.mod` в `$GOBIN`.

## Сравнение подходов

| | `tools.go` (до 1.24) | `tool` в `go.mod` (1.24+) |
|---|---|---|
| Файл | Отдельный `tools.go` | Ничего лишнего |
| Build-тег | Нужен (`//go:build tools`) | Не нужен |
| Импорты | `import _ "..."` | Директива `tool` |
| Установка | `go install <путь>` вручную | `go install tool` |
| Централизация | Размазана | В `go.mod` |

**Вывод:** новый подход **чище**. Если Go 1.24+ — используй `tool`.

## Миграция со старого на новый

1. Убедись, что Go **1.24+**.
2. Удали `tools.go`.
3. Выполни:
   ```bash
   go get -tool golang.org/x/tools/cmd/stringer@latest
   ```

Всё. Инструменты теперь в `go.mod`.

## go generate

**Что это:** встроенная утилита Go для **генерации кода**. **Не часть компиляции**, а инструмент разработчика.

### Синтаксис

В `.go` файле — комментарий:

```go
//go:generate команда
```

Запуск:

```bash
go generate ./...       # все пакеты
go generate             # только текущий
```

### Пример

```go
package main

import "fmt"

//go:generate stringer -type=Pill

type Pill int

const (
	Placebo Pill = iota
	Aspirin
	Ibuprofen
	Paracetamol
	Acetaminophen = Paracetamol
)

func main() {
	fmt.Printf("For headaches, take %v\n", Ibuprofen)
}
```

```bash
go generate ./...
# создаст pill_string.go с методом String() для Pill
```

### Когда использовать go generate

| Задача | Инструменты |
|---|---|
| Моки | `mockery`, `moq`, `gomock` |
| Stringer | `stringer` |
| Protobuf | `protoc-gen-go` |
| Deep-copy | `deepcopy-gen` |
| Enum | `go-enum` |
| OpenAPI | `oapi-codegen` |
| Сериализация | `ffjson` |

### ⚠️ Важно помнить

| Правило | Смысл |
|---|---|
| **Не запускается автоматически** | Только `go generate` вручную |
| **Не влияет на `go build`** | Это не часть сборки |
| **Обычные shell-команды** | Из текущей директории |
| **Требует установленных инструментов** | `go install` перед запуском |

## Рекомендации

| № | Правило |
|---|---|
| 1 | Фиксируй версии инструментов — стабильность и предсказуемость |
| 2 | С Go 1.24+ — используй `tool` в `go.mod` |
| 3 | Регулярно обновляй инструменты, но **проверяй совместимость** |
| 4 | Документируй используемые версии в проекте |
| 5 | `go generate` — явно, вручную, не в `go build` |

## Подводные камни

### 1. `go generate` не запускается сам

Забыл вызвать — генерация **не произошла**. В CI нужно **явно** добавить шаг `go generate ./...`.

### 2. `$GOBIN` не в `PATH`

Если `~/go/bin` не в `$PATH` — `go install` положит бинарник, но **терминал его не найдёт**. Решение:
```bash
export PATH=$PATH:$(go env GOPATH)/bin
```

### 3. `tool` требует Go 1.24+

На старых версиях — **не скомпилируется**. Проверь `go version`.

### 4. `tools.go` может конфликтовать с `tool`

После миграции на `tool` — **удали `tools.go`**, иначе будет путаница.

### 5. Сгенерированный код тоже коммитится

`pill_string.go` и подобные — **в git**. Иначе без `go generate` сборка упадёт.

## Запомнить

- **Фиксируй версии инструментов** — иначе разнобой в команде.
- **Старый подход:** `tools.go` с `//go:build tools` и импортом через `_`.
- **Новый (Go 1.24+):** директива `tool` в `go.mod`.
- **`go get -tool <pkg>`** — добавить инструмент.
- **`go install tool`** — установить все инструменты из `go.mod`.
- **`go generate ./...`** — запустить генерацию кода.
- **`//go:generate <команда>`** — директива в `.go` файле.
- **`go generate` — вручную.** Не часть сборки.
- **`$GOBIN`** (`~/go/bin`) должен быть в `PATH`.
- **Сгенерированный код — в git.**
