# Интерфейсы (Interfaces)

**Главное:** интерфейс — это набор **методов** (поведение), а не реализация. Тип удовлетворяет интерфейсу **неявно**: если реализовал все методы — ты уже реализация. Никакого `implements` писать не нужно. Это **duck typing**: «если выглядит как утка и крякает как утка — это утка».

## Объявление и неявная реализация

```go
type Speaker interface {
    Speak() string
}

type Human struct{ Name string }

func (h Human) Speak() string {
    return "Hello, my name is " + h.Name
}

var s Speaker = Human{Name: "Alice"}   // ✅ Human реализует Speaker
fmt.Println(s.Speak())
```

**Ключевое:**
- Реализация — автоматическая, если сигнатуры методов совпадают.
- Интерфейс может быть объявлен **в другом пакете** — тип всё равно его реализует.

## Явная проверка реализации (compile-time)

Гарантирует на этапе **компиляции**, что тип реализует интерфейс. Полезно, когда интерфейс в другом пакете.

```go
var _ Speaker = (*Human)(nil)
```

| Часть | Смысл |
|---|---|
| `var _ Speaker` | переменная типа `Speaker`, `_` = «не использовать» |
| `(*Human)(nil)` | nil-указатель на `Human` |
| Вся строка | если `*Human` **не** реализует `Speaker` → **ошибка компиляции** |

**Зачем:** защита от регрессий. Удалил метод — код не соберётся, узнаешь сразу.

⚠️ **Нюанс:** если метод на **pointer receiver** — нужен `(*Human)`. Если на value receiver — можно `Human` или `(*Human)`.

**Альтернатива:** комментарий `// Human implements Speaker` — это документация, компилятор её **не проверяет**.

## Пустой интерфейс

`interface{}` (синоним `any` с Go 1.18) — интерфейс **без методов**. Ему удовлетворяет **любой тип**.

```go
func PrintValue(v interface{}) {
    fmt.Println(v)
}

PrintValue(42)
PrintValue("Hello")
PrintValue([]int{1, 2})
```

**Когда:** тип значения неизвестен заранее (логирование, JSON, обобщённые контейнеры).

⚠️ **Избыточное использование** → теряешь типизацию и читаемость. Если знаешь типы — бери конкретный интерфейс или дженерики.

## Type assertion (приведение типа)

```go
if value, ok := v.(int); ok {
    fmt.Println("Integer value:", value)
} else {
    fmt.Println("Unknown type")
}
```

| Форма | Поведение |
|---|---|
| `v.(T)` | **паника**, если `v` не типа `T` |
| `v, ok := v.(T)` | **безопасно**: `ok = false`, если не совпал |

**Правило:** в проде — **всегда с `ok`**. Без `ok` — только если абсолютно уверен в типе.

## Type switch

```go
switch v := v.(type) {
case int:
    fmt.Println("Integer:", v)   // v — int
case string:
    fmt.Println("String:", v)    // v — string
default:
    fmt.Println("Unknown type")
}
```

- Внутри `case` переменная `v` **уже нужного типа**.
- `default` — обязателен, если не уверен в покрытии.

## Нулевые интерфейсы — главная ловушка

**Правило:** интерфейс считается `nil` **только если и тип, и значение внутри — nil**.

```go
var i interface{} = nil
fmt.Println(i == nil)    // true

var p *int = nil
var j interface{} = p
fmt.Println(j == nil)    // false ❗
```

**Устройство интерфейса под капотом** — это пара `(тип, значение)`:

| Ситуация | Тип | Значение | `== nil`? |
|---|---|---|---|
| `var i interface{} = nil` | nil | nil | ✅ true |
| `var j interface{} = (*int)(nil)` | `*int` | nil | ❌ false |

Во втором случае **тип задан** (`*int`), поэтому интерфейс **не пустой**, хотя значение внутри nil.

**Как проверить, что внутри nil-указатель:**

```go
if ptr, ok := j.(*int); ok && ptr == nil {
    fmt.Println("внутри nil указатель")
}

// или через reflect
if reflect.ValueOf(j).IsNil() {
    fmt.Println("внутри nil")
}
```

⚠️ **Где стреляет:** функция возвращает `error`, но внутри — nil-указатель на структуру. Переменная `error != nil`, хотя «по логике» ошибки нет. Ты **пропускаешь ошибку**, думая, что её нет.

## Duck typing

Совместимость — по **набору методов**, а не по имени типа.

```go
type Walker interface{ Walk() string }

type Dog struct{}
func (d Dog) Walk() string { return "The dog is walking" }

type Robot struct{}
func (r Robot) Walk() string { return "The robot is walking" }

func MakeWalk(w Walker) { fmt.Println(w.Walk()) }

MakeWalk(Dog{})
MakeWalk(Robot{})
```

## Композиция интерфейсов

Интерфейсы **встраивают** друг друга — получается составной интерфейс.

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}

type Writer interface {
    Write(p []byte) (n int, err error)
}

type ReadWriter interface {
    Reader
    Writer
}
```

Любой тип, реализующий **оба** метода, автоматически удовлетворяет `ReadWriter`.

## Встраивание структур

Работает и для **структур**: встроенный тип «отдаёт» свои методы.

```go
type Logger struct{}
func (l Logger) Log(msg string) { fmt.Println(msg) }

type Service struct {
    Logger   // встроенное поле
}

s := Service{}
s.Log("Hello, world!")   // метод Logger доступен через Service
```

## Лучшие практики

| № | Практика | Почему |
|---|---|---|
| 1 | Интерфейсы — **маленькие** (1–2 метода) | Проще комбинировать, легче реализовать |
| 2 | Использовать интерфейсы **для абстракции**, а не везде | Не плодить лишние уровни |
| 3 | Избегать `interface{}`, если известны типы | Теряется типизация, растут проверки |
| 4 | Использовать **стандартные** (`io.Reader`, `io.Writer`, `error`) | Единый стиль, совместимость |
| 5 | Не бояться возвращать конкретные типы | Абстракция нужна не всегда |
| 6 | Интерфейсы — для **моков в тестах** | Позволяет подменять реальные зависимости |

## Подводные камни

### 1. `interface{}` != `nil`, если внутри nil-указатель
Классическая ошибка в обработке ошибок. Интерфейс смотрит на **пару (тип, значение)**, а не только на значение.

### 2. Type assertion без `ok` → паника
В проде — только `v, ok := i.(T)`.

### 3. `interface{}` вместо конкретного типа → теряешь проверки компилятора
Растут `switch` и `ok`-проверки, код становится хрупким.

### 4. Интерфейс с большим количеством методов — плохой дизайн
Дроби на маленькие (как `io.Reader` / `io.Writer`).

### 5. `var _ I = (*T)(nil)` — про pointer vs value receiver
Если метод на **pointer receiver** — обязательно `(*T)`. Иначе компилятор скажет, что `T` не реализует `I`.

## Запомнить

- **Интерфейс = набор методов.** Реализация — **неявная**.
- `var _ Speaker = (*Human)(nil)` — **compile-time проверка** реализации.
- **`interface{}` / `any`** — пустой интерфейс, принимает любой тип.
- **Type assertion:** `v, ok := i.(T)` — с `ok`. Без `ok` — паника.
- **Type switch:** `switch v := i.(type)` — переменная внутри `case` уже нужного типа.
- **Интерфейс под капотом — пара `(тип, значение)`.**
- **`nil`-интерфейс ≠ интерфейс с `nil`-значением.** Проверка `i == nil` требует, чтобы **и тип, и значение** были nil.
- **Композиция интерфейсов** — через встраивание (`Reader`, `Writer` → `ReadWriter`).
- **Встраивание структур** — «отдаёт» методы встроенного типа.
- **Интерфейсы — маленькие.** Один-два метода.
- **`interface{}` — только когда тип реально неизвестен.** Иначе — конкретный интерфейс.

# Тонкости ресивера и Method Set

**Главное:** в Go интерфейс проверяется **не по принципу «есть похожий метод»**, а по **набору методов типа** (method set). У типа `T` и указателя `*T` эти наборы **различаются**. Именно поэтому структура «вроде бы подходит» под интерфейс, а компилятор не согласен.

## Что такое Method Set

**Method set** — набор методов, принадлежащих типу. Компилятор использует его, когда проверяет, удовлетворяет ли тип интерфейсу.

| Тип | Набор методов |
|---|---|
| `T` | только методы с ресивером `T` |
| `*T` | методы с ресивером `T` **И** методы с ресивером `*T` |

То есть **`*T` «богаче»**: он видит все методы, а `T` — только свои.

## Классическая ошибка

```go
type Speaker interface {
    Speak()
}

type User struct {
    Name string
}

func (u *User) Speak() {     // ⚠️ pointer receiver
    fmt.Println("Привет, я", u.Name)
}

func main() {
    u := User{Name: "Анна"}

    var s Speaker
    s = u   // ❌ ошибка компиляции
    s.Speak()
}
```

**Ошибка компилятора:**
```
cannot use u (variable of type User) as Speaker value in assignment:
    User does not implement Speaker (method Speak has pointer receiver)
```

**Почему так:** метод `Speak()` объявлен с ресивером `*User`, значит он входит в набор методов **только `*User`**, но не `User`. Интерфейс реализует **указатель**, а не значение.

**Как исправить:**

```go
s = &u   // ✅ *User реализует Speaker
```

или сразу создавать указатель:

```go
u := &User{Name: "Анна"}   // *User
var s Speaker = u
s.Speak()
```

## Главное правило ресиверов

| Объявление метода | Входит в набор `T` | Входит в набор `*T` |
|---|---|---|
| `func (t T) Method()` | ✅ | ✅ |
| `func (t *T) Method()` | ❌ | ✅ |

**Следствие:**
- Метод на **значении** → интерфейс реализуют **и `T`, и `*T`**.
- Метод на **указателе** → интерфейс реализует **только `*T`**.

## Три варианта на практике

### Вариант 1. Метод на значении — самый гибкий

```go
func (u User) Speak() {
    fmt.Println("Привет, я", u.Name)
}

u := User{Name: "Анна"}

var s1 Speaker = u    // ✅ ok
var s2 Speaker = &u   // ✅ тоже ok
User{Name: "Анна"}.Speak()   // ✅ можно вызвать у анонимного объекта
```

Метод доступен **и для `User`, и для `*User`** → интерфейс реализуют оба.

### Вариант 2. Метод на указателе — только `*T`

```go
func (u *User) Speak() {
    fmt.Println("Привет, я", u.Name)
}

u := User{Name: "Анна"}

var s Speaker
// s = u    // ❌ User не реализует Speaker
s = &u      // ✅ ok

// User{Name: "Анна"}.Speak()   // ❌ нельзя pointer method на value
(&User{Name: "Анна"}).Speak()   // ✅ ok
```

Метод доступен **только для `*User`** → интерфейс реализует только указатель.

### Вариант 3. Метод на nil-указателе — поведение зависит от реализации

```go
type User struct { Name string }
func (u *User) Speak()  { fmt.Println("Привет, я", u.Name) }

type Admin struct{}
func (a Admin) Speak()  { fmt.Println("Привет, я админ") }

type Guest struct { Name string }
func (g *Guest) Speak() {
    if g == nil {
        fmt.Println("Привет, я гость")
    } else {
        fmt.Println("Привет, я гость", g.Name)
    }
}

var a *Admin   // nil
var u *User    // nil
var g *Guest   // nil

var s Speaker
s = u
// s.Speak()   // 💥 panic: nil pointer dereference (u.Name на nil)

s = a
// s.Speak()   // 💥 panic: value method called using nil *Admin pointer

s = g
s.Speak()      // ✅ "Привет, я гость" — внутри проверка if g == nil
```

| Тип | nil-указатель внутри интерфейса | Что происходит при `Speak()` |
|---|---|---|
| `*User` (pointer receiver, обращается к полю) | допустимо | 💥 паника (разыменование nil) |
| `*Admin` (value receiver) | допустимо | 💥 паника (value method на nil-указателе) |
| `*Guest` (pointer receiver + проверка `if g == nil`) | допустимо | ✅ безопасно |

**Вывод:** nil-указатель **можно** положить в интерфейс, если тип реализует его. Но **безопасность вызова — на совести реализации метода**. Если метод не проверяет nil и работает с полями — паника.

## Проверка реализации на этапе компиляции

```go
var _ Speaker = (*User)(nil)
var _ Speaker = (*Guest)(nil)
var _ Speaker = (*Admin)(nil)
```

**Что здесь:**
- `var _ Speaker` — переменная типа `Speaker`, `_` = «не использовать».
- `(*User)(nil)` — nil-указатель на `User`.
- Компилятор проверяет: можно ли присвоить `*User` интерфейсу `Speaker`.
- Если **нет** — программа **не скомпилируется**.

**Объекты не создаются.** Это **чистая проверка типов на этапе компиляции**.

**Когда полезно:**
- Интерфейс и реализация — **в разных пакетах**.
- Хочешь **явно зафиксировать** в коде: «этот тип должен реализовывать интерфейс».
- Интерфейс **может измениться** — компилятор сразу скажет.

⚠️ **Нюанс:** если метод на pointer receiver — пиши `(*User)`. Если на value — работает и `User`, и `(*User)`.

## Подводные камни

### 1. «Метод есть — значит, реализую» — неверно
Метод с pointer receiver **не входит** в набор методов `T`. Интерфейс реализует только `*T`.

### 2. `T` vs `*T` — это разные наборы методов
`*T` видит **все** методы. `T` — **только value-методы**.

### 3. nil-указатель в интерфейсе — не ошибка компиляции
Компилятор пропустит. Паника — только в рантайме, если метод не готов к nil.

### 4. `var _ I = (*T)(nil)` — не создаёт объект
Это **проверка типов**, не выполнение кода.

### 5. Смешивать value/pointer receiver в одном типе — плохо
Если хоть один метод на `*T` — делай **все** на `*T`. Иначе будешь путаться, какие методы в каком наборе.

## Запомнить

- **Method set** определяет, реализует ли тип интерфейс.
- `T` видит только методы с ресивером `T`.
- `*T` видит методы с ресивером `T` **и** `*T`.
- Метод на **значении** → интерфейс реализуют **и `T`, и `*T`**.
- Метод на **указателе** → интерфейс реализует **только `*T`**.
- `func (u *User) Speak()` → `s = &u` ✅, `s = u` ❌.
- **nil-указатель** можно положить в интерфейс, если тип реализует интерфейс.
- Вызов метода на nil-указателе: **паника**, если метод не проверяет `nil`.
- `var _ Interface = (*Type)(nil)` — **compile-time проверка** реализации.
- **Не смешивай** value/pointer receiver в одном типе.

# Слайсы и карты интерфейсов

**Главное:** `[]interface{}` и `map[interface{}]interface{}` позволяют хранить **разнородные данные** в одной коллекции. Но за гибкость платишь: **нет типизации, нужны проверки типов, падает производительность** (boxing). Использовать только когда структура данных реально неизвестна.

## Слайсы интерфейсов ([]interface{})

### Неявного преобразования нет

Слайс конкретного типа **нельзя** присвоить `[]interface{}` напрямую:

```go
strings := []string{"Go", "is", "awesome"}
// var interfaces []interface{} = strings   // ❌ ошибка компиляции

// Решение: явное преобразование поэлементно
interfaces := make([]interface{}, len(strings))
for i, s := range strings {
    interfaces[i] = s
}
```

**Причина:** каждый элемент должен быть **явно упакован** в `interface{}`. Слайс — это не «контейнер ссылок», а последовательность значений **фиксированного типа**. `[]string` и `[]interface{}` — **разные типы** в памяти.

### Приведение типов при извлечении

Нужен `type switch` или `type assertion`:

```go
data := []interface{}{42, "Hello", true}

for _, v := range data {
    switch v := v.(type) {
    case int:
        fmt.Println("Integer:", v)
    case string:
        fmt.Println("String:", v)
    case bool:
        fmt.Println("Boolean:", v)
    default:
        fmt.Println("Unknown type")
    }
}
```

### Производительность

Каждый элемент **упаковывается** (boxing) в интерфейс — это выделение памяти и накладные расходы. Для типизированных данных — **используй `[]T`**, а не `[]interface{}`.

## Карты с интерфейсами (map[interface{}]interface{})

### Гибкость без типизации

```go
data := make(map[interface{}]interface{})

data["name"] = "Go"
data[1] = 42
data[true] = false

fmt.Println(data)   // map[1:42 true:false name:Go]
```

Ключи и значения — **любых типов**. Компилятор не поможет: ошибёшься в типе ключа — узнаешь только в рантайме.

### Приведение типов

```go
data := map[interface{}]interface{}{
    "name": "Go",
    1:      42,
    true:   false,
}

for k, v := range data {
    switch k := k.(type) {
    case string:
        fmt.Printf("Key: %s, Value: %v\n", k, v)
    case int:
        fmt.Printf("Key: %d, Value: %v\n", k, v)
    default:
        fmt.Printf("Unknown key type: %v\n", k)
    }
}
```

### Ключи разных типов — разные записи

```go
data[1]   // ключ типа int
data["1"] // ключ типа string
```

Это **разные ключи**. Уникальность определяется **типом + значением**, а не «похожестью».

### Производительность

Boxing ключей и значений → накладные расходы. Использовать только когда структура данных **реально неизвестна**.

## Когда использовать

| Ситуация | Инструмент |
|---|---|
| Элементы **разных типов** в одной коллекции | `[]interface{}` |
| Данные **неизвестной структуры** (парсинг, конфиги) | `map[interface{}]interface{}` |
| Универсальное логирование | `[]interface{}` |
| Структура **известна** | Типизированные `[]T` / `map[K]V` |

**Примеры:**

```go
// Логирование
log := []interface{}{"Error:", 404, true}

// Динамический конфиг
config := map[interface{}]interface{}{
    "timeout": 30,
    "debug":   true,
    "name":    "my-app",
}
```

## Рекомендации

| № | Правило |
|---|---|
| 1 | Использовать интерфейсы **только при необходимости** |
| 2 | Если структура известна → **типизированные** слайсы и карты |
| 3 | Всегда проверять тип (`type assertion` / `switch`) |
| 4 | Документировать ожидаемую структуру (комментарий / README) |
| 5 | Минимизировать упаковку в `interface{}` — это производительность |

## Подводные камни

### 1. `[]string` ≠ `[]interface{}`
Слайс конкретного типа **нельзя** присвоить `[]interface{}` — только поэлементно.

### 2. Type assertion обязателен
Из `[]interface{}` или `map[interface{}]interface{}` достаёшь `interface{}` — нужен `switch` или `v, ok := x.(T)`.

### 3. `1` и `"1"` — разные ключи
Разный **тип** ключа → разные записи. Даже если значение «похоже».

### 4. Boxing = производительность
Каждая упаковка — накладные расходы. На горячих участках — типизированные коллекции.

### 5. Потеря проверок компилятора
Опечатка в ключе или типе значения — узнаешь только в рантайме, не на этапе компиляции.

## Запомнить

- `[]interface{}` / `map[interface{}]interface{}` — для **разнородных** данных.
- `[]string` **нельзя** присвоить `[]interface{}` — только **поэлементно**.
- Для извлечения нужен **type assertion** или **type switch**.
- Ключи **разных типов** — разные записи (`1` ≠ `"1"`).
- **Boxing** → накладные расходы. Типизированные коллекции быстрее.
- Структура известна → **бери типизированные** `[]T` / `map[K]V`.
- Использовать `interface{}` — **только при реальной необходимости**.
